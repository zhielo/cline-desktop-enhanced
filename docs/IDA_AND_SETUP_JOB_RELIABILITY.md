# Integrated IDA and Setup Center reliability

## Fixed behavior

- IDA database compatibility binds target bytes, selected engine executable, engine configuration and the database adapter version. It excludes the selected function and output script identity. Output identity still includes the selector, and each request actually runs its selected-function adapter; one function's pseudocode is never returned as another's cached output.
- Every supervised IDA run uses a separate private attempt directory under the existing cross-process workspace lease. Compatible packed databases are integrity-checked and copied into that attempt. Fresh runs use an unused `-o` destination. Existing accepted, failed and legacy databases/logs remain intact. GUI handoff can open a private copy of a compatible accepted snapshot; it never publishes an unobserved GUI session as completed analysis. The accepted pointer is updated atomically only after confirmed successful execution and a nonempty, bounded, regular saved database; this is lifecycle and digest verification, not an independent IDA database parser or semantic correctness proof. A failed run does not replace the previous accepted snapshot. Unconfirmed termination retains the existing workspace lease.
- Built-in `analyze` attaches a fixed IDAPython lifecycle script: input loaded, auto-analysis waiting/completed, database saving/saved, explicit exit. It does not require Hex-Rays. Decompile scripts also explicitly save their databases. Phase supervision applies only to supported fixed scripts; user scripts retain the original overall timeout without falsely requiring Cline's private phase protocol. No automatic execution retry or blanket timeout increase is added.
- Old hash-keyed cache files are preserved, not automatically deleted or silently trusted as new compatible snapshots. The first new-version request may perform a fresh analysis in its separate attempt. Subsequent compatible requests can reuse it across selected functions. Attempt directories deliberately retain forensic output; there is no automatic deletion of project/analysis files in this upgrade.

## Setup operations

Trusted, explicitly confirmed pack install/test/rollback and IDA/device/worker tests can return an immediate persisted job ID. Existing synchronous callers remain supported. A cross-process exclusive admission lease rejects competing setup changes; identical concurrent requests in one owning host coalesce. Job phases describe actual coarse setup stages, not percentage/engine progress. The GUI displays the job beside its actions and uses serialized read-only polling, stops polling on unmount, and rejoins saved host state on navigation/reconnect. A response timeout does not imply installation failure and never causes replay. Terminal job summaries are bounded to the latest 32; credentials and request arguments are not stored, and failure text uses the existing bounded secret redactor.

A running record after loss/restart of its owning backend is **interrupted / termination unconfirmed**, not successful or automatically restarted. Admission is retained rather than stolen based on PID/name alone. Operator-confirmed termination/recovery remains necessary in that exceptional case; restarting the GUI alone does not prove analysis subprocesses exited. The job feature does not claim automatic recovery across an unconfirmed host crash.

All eleven full-pack engines still require owned-fixture execution receipts. Installer resource integrity, independent angr interpreter, core rollback, idle-only Hub restart and no-prompt-replay rules remain unchanged. A completed setup command is not itself a capability-readiness receipt.

## IDA setup

**Save IDA installation** saves the explicit folder independently of the optional integration test. The runtime executor does not consult Setup Center's acceptance receipt as an execution gate. Selecting/detecting a folder is not proof of IDAPython, all processor plugins, licensing or target compatibility. Actual engine launch/plugin/decompiler errors remain authoritative; licensed processor fixtures remain available as an optional diagnostic. Processor choice survives settings navigation. Applying saved settings to an already-running shared Hub still uses the separate idle-only action.

## Acceptance

Blocking regressions cover changed selectors, isolated fresh runs, stale/altered snapshots, fixed analyze/save/exit scripting, supported phase deadlines, unsupported-script overall deadlines, setup admission/coalescing, retained crash uncertainty, redacted terminal state, UI read-only rejoin and response-timeout semantics, optional testing and processor persistence. Installed Windows journeys additionally exercise persisted processor selection and the full-pack tracked completion job, retaining all eleven engine checks, backend restart, saved-session recovery and core rollback. Hosted fixtures do not claim a real commercial IDA/Hex-Rays license test; the owner's supplied real-host test evidence remains separate from this build's mock-protocol regressions.
