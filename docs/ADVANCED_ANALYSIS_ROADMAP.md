# Advanced analysis: implementation ledger and acceptance criteria

This ledger prevents partial implementations from being described as the entire roadmap. It records **code coverage**, not installed-tool readiness, licensed-engine access, target compatibility or deployment to the user's computer. Hosted current-head release checks remain mandatory before merging.

## Current implementation batch

- **Implemented, pending release validation:** up to 32 non-overlapping exact binary byte edits or primitive JS/TS literal edits per candidate. Existing single-edit recipes remain supported. Original hashes, all original offsets, new destination and every edit bind the preview; application requires separate approval. Aggregate budgets and overlap checks fail closed. Originals are preserved; native checksums, relocations, code signatures and semantic correctness are not repaired or certified.
- **Implemented, pending release validation:** `trace_source_sink` searches validated saved evidence from up to 16 sources to 16 sinks. Default `data-flow` mode excludes all other edge kinds. Explicit `declared-relationships` mode retains candidate relationship confidence. User stop IDs are traversal boundaries, not verified sanitizers. Results contain bounded witness paths, provenance, visited counters and partial coverage, never a claim of whole-program taint or observed runtime behavior.
- **Implemented, pending release validation:** `audit_candidate_batch` reads original inputs and existing candidate files, recomputes exact recipe hashes and reports verified/missing/mismatch/unverified stages. It writes nothing and does not authenticate the artifact producer. Only a clean audit proposes missing IDs; any mismatch or unverified source blocks recovery suggestions. Recovery requires a new confined manifest, a fresh preview and separate approval. No blind replay, overwrite, cleanup or rollback is performed by an audit.
- **Implemented, pending release validation:** GUI preparation templates, model tool schema/catalog, blocking unit coverage and installed Windows acceptance for multi-edits, auditing and source/sink queries. Existing provider/session settings, reasoning persistence, Android build/sign tools and runtime approval gates remain unchanged.

## Usage

For multi-edit binary candidates, use `candidate.byte_patches` instead of `candidate.byte_patch`; for multi-edit JS/TS use `candidate.literals` instead of `candidate.literal`. Do not mix single and plural recipes. Each literal uses its original UTF-16 `start`, exact `expected` text and primitive `replacement`. Each byte edit uses original `offset`, exact `expected_hex` and equal-length `replacement_hex`. Preview and apply remain distinct requests.

For source/sink search, set `target` to a saved validated report and `source_sink` to `{ "source_ids": ["..."], "sink_ids": ["..."], "stop_ids": [], "relation": "data-flow" }`. IDs must exist. Traversal respects depth/state/edge/output budgets. Missing witnesses are not proof of absence of behavior.

For recovery review, set `operation` to `audit_candidate_batch` and `target` to the original manifest. A partial audit is informational, not permission to rerun. Investigate mismatches first; review proposed remaining IDs, prepare a **new** manifest, then separately preview and approve it.
